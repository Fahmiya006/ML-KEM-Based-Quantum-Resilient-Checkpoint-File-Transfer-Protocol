PQ6G Transfer evidence

A file sent through a simulated 6G link with ML-KEM-768 key exchange, AES-256-GCM chunks and signed checkpoints. Every number below comes from a real run of the code in this project (sender, link emulator and receiver as separate components over TCP on one machine).

What is real and what is simulated. Real: ML-KEM-768 (FIPS 203), AES-256-GCM, SHA-256 hash chain, HMAC-signed checkpoints, files written and fsynced to disk, TCP connections that are actually cut. Simulated: the 6G radio (rate limit, delay and random blockages applied by a relay) and the quantum computer (Shor's algorithm run on a classical state-vector simulator against an 11-bit toy RSA key). These runs happened in a cloud sandbox over loopback, not on your laptop and phone. The phone path is untested here.

S8. Simulated quantum computer, harvest now, decrypt later

An eavesdropper recorded the whole transfer (20 MiB, 647 frames) from the air interface. Later a quantum computer attacks the recording. Same file, same link, two different key exchanges.

Toy RSA key exchange (N = 1769)

Shor's algorithm, run as a state-vector simulation on 33 logical qubits, found the period on its second attempt (order 420) and factored N = 29 × 61. The recorded session key followed, and all 320 chunks decrypted. The recovered file is byte-identical to the original; its first bytes are this banner:

ML-KEM-768 key exchange

Shor needs a factoring or period-finding problem, and the recording has none. The public key and ciphertext are lattice data (Module-LWE). The attacker tried 144,500 random AES keys in 3 s (0 authenticated); the 2^256 key space would take about 10^64 years, and Grover's search would still need 2^128 steps. The recording stays encrypted.

Below: the first 63,000 bytes the eavesdropper recorded, one byte per pixel (measured entropy 8.00 of 8 bits per byte).

The RSA key here is 11 bits, so a laptop can break it classically in microseconds. It exists to show the pipeline (capture, find the period, derive the key, decrypt, compare) end to end. Real RSA-2048 is out of reach for any simulator.

On this setup N between 1 and 32 are indistinguishable (about 5 s); from N = 64 up, the extra re-sent data costs about 2.7 s more. Small N saves less data per cut but adds nothing noticeable here because loopback disk flushes are quick. A phone's flash storage is slower, so the optimum there will sit at a larger N; the receiver has a --ckpt-delay-ms option to try that.

Checks that passed

17 of 17 self-tests: HKDF and SHA-256 test vectors, GCM rejects flipped bits, wrong chunk numbers and wrong sessions, every one of the 672 single-bit changes to a checkpoint is rejected, the pure-Python ML-KEM interoperates with the native one in both directions, a process killed 40 times in the middle of writing checkpoints never left a corrupt one, and an end-to-end transfer survives a cut with one key exchange.

Where this differs from the project guide

The receiver picks the session id and the sender speaks first (START), for simpler resume. The sender compares the receiver's hash chain against its own at resume time, which the guide described but did not implement. The persistence of keys on the receiver (S4) is an addition. The checkpoint cost includes the data flush.
